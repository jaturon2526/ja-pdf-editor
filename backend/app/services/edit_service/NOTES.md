# edit_service — แนวทางและประวัติการแก้บั๊ก

(ย้ายมาจาก docstring ของ edit_service.py เดิม ตอนแยกเป็น package — หมายเลข "แก้บั๊กสำคัญ #N" ในโค้ดอ้างถึงหัวข้อในไฟล์นี้)

> ไฟล์นี้เป็นประวัติการตัดสินใจ ส่วนที่อธิบายวิธีวาดข้อความ (#2) และการตัดบรรทัดปรับให้ตรงกับโค้ดปัจจุบันแล้ว (ต.ค. 2026)

edit_service — แก้ไขข้อความและรูปภาพในหน้า PDF (ข้อ 5 ของโจทย์)

แนวทางแก้ข้อความ: PDF ไม่มีแนวคิด "แก้ข้อความในตำแหน่งเดิม" ตรงๆ เหมือนไฟล์ text
วิธีที่ใช้กันจริงคือ "redact แล้ววาดใหม่"
  1. get_text_blocks() — จัดกลุ่มบรรทัดข้อความในหน้าเป็นระดับ "ย่อหน้า" โดยรวมเฉพาะบรรทัดที่ดู
     เป็นการ "wrap" ของย่อหน้าเดียวกันจริงๆ (ดูหมายเหตุเรื่องบั๊ก paragraph ผสมกันด้านล่าง)
     พร้อม bbox รวมทั้งย่อหน้า ส่งให้ frontend แสดงเป็นกล่องคลิกเลือกทับบนรูป preview —
     ผู้ใช้เลือกได้ทีเดียวทั้งย่อหน้า ไม่ต้องไล่เลือกทีละ span/บรรทัด
  2. ผู้ใช้คลิกเลือกย่อหน้าที่จะแก้ + พิมพ์ข้อความใหม่ + เลือก font/สี/ขนาดจาก properties panel
     ส่งกลับมาพร้อม bbox เดิม (ดู TextEditRequest)
  3. replace_text() ลบข้อความเดิมทั้งย่อหน้าด้วย redaction (วาดทับด้วยสีพื้นหลัง) แล้ว "ตัดคำ"
     ข้อความใหม่ให้พอดีความกว้างของกล่องเดิมก่อนวาดทับ

เรื่อง font ภาษาไทย (แก้บั๊กสำคัญ #1): เดิมโค้ดนี้ fallback ไปใช้ font มาตรฐานของ PyMuPDF (helv/times/...)
เสมอเวลาวาดข้อความใหม่ ซึ่งเป็น font ละตินล้วน "ไม่มี glyph ภาษาไทยเลย" — ผลคือแก้ข้อความภาษาไทย
แล้วไม่เห็นอะไรขึ้นมาเลย (ช่องว่างเปล่า) ทางแก้คือ bundle font TrueType ที่รองรับไทยจริง
(ดู app/services/fonts.py)

เรื่องวรรณยุกต์ทับสระ (แก้บั๊กสำคัญ #2): หลังแก้บั๊ก #1 แล้วพบว่า page.insert_text()/insert_htmlbox()
ของ PyMuPDF วาดตัวอักษรแบบ "เรียง glyph ตาม cmap + advance width เฉยๆ" ไม่ได้ทำ OpenType complex-script
shaping (ไม่มี GPOS mark-to-base/mark-to-mark) ผลคือพยางค์ไทยที่มีทั้งสระบนกับวรรณยุกต์ซ้อนกัน (เช่น
"ที่", "สั่ง", "ซื้อ") พอเอามาต่อกันหลายพยางค์ ตำแหน่ง mark จะเพี้ยน/ทับกันไม่เรียงซ้อนขึ้นบนให้ถูกต้อง
(reproduce แล้วยืนยันว่าเกิดกับทั้ง insert_text และ insert_htmlbox เหมือนกันทุกประการ — ไม่ใช่ปัญหาที่
API ตัวใดตัวหนึ่ง แต่เป็นข้อจำกัดของ text-layout engine ใน MuPDF เองที่ไม่รองรับ complex script shaping)
ทางแก้ (ปัจจุบัน): สร้าง PDF จิ๋วหนึ่งหน้าด้วย fpdf2 เปิด text shaping (`set_text_shaping(True, script="thai")`
ซึ่งใช้ uharfbuzz ทำ GPOS/GSUB ตาม OpenType ของฟอนต์) แล้ววางทับตำแหน่งเดิมด้วย `page.show_pdf_page()`
(ดู text.replace_text ขั้น "4) เรนเดอร์ข้อความผ่าน fpdf2 + uharfbuzz") — ข้อความยังเป็นเวกเตอร์ เลือก/ค้นหา/
คัดลอกได้ และคมทุกระดับซูม
(รุ่นแรกเรนเดอร์ผ่าน Pillow + RAQM เป็นรูป PNG แล้ว insert_image — ข้อความที่แก้แล้วกลายเป็นรูป ค้นหาไม่ได้
จึงเลิกใช้ Pillow ในการแก้ข้อความ; ปัจจุบัน Pillow + RAQM เหลือใช้แค่ข้อความบนตราลายเซ็นดิจิทัล
signature_service — main.py เตือนใน log ตอน start ถ้า Pillow ไม่มี RAQM)

เรื่องการตัดบรรทัด (word wrap): ภาษาไทยเขียนติดกันไม่มีเว้นวรรคระหว่างคำ จะตัดบรรทัดแบบเดียวกับ
ภาษาอังกฤษ (ตัดตรงช่องว่าง) ไม่ได้ ต้อง "ตัดคำ" ก่อนถึงจะขึ้นบรรทัดใหม่ได้สวยงามโดยไม่ตัดกลางคำ —
ใช้ thai_text.tokenize (pythainlp newmm + คำเสริมใน app/assets/thai_custom_words.txt) ตัดคำ แล้ววัด
ความกว้างจริงด้วย FPDF ที่เปิด text shaping แบบเดียวกับตอนวาด (layout._get_fpdf_for_font) ก่อนไล่จัดคำ
เข้าบรรทัดแบบ greedy ให้พอดีความกว้างกล่องเดิม (layout._wrap_text) — หน่วยที่ห้ามแยก เช่น "มาก ๆ",
"(ไทย)" และคำที่ยาวเกินกล่องตัดที่ขอบพยางค์

เรื่องบั๊ก paragraph ปนกัน (แก้บั๊กสำคัญ #3): เอกสารแบบฟอร์ม/ใบแจ้งหนี้มักมีบรรทัดสั้นๆ ของคนละ field
(เช่น "ชื่อลูกค้า :" ตามด้วยชื่อคนละบรรทัด ตามด้วย "เลขที่ใบสั่งซื้อ :" ของอีก field) วางอยู่ใกล้กัน
จนกลไก layout analysis ของ MuPDF (page.get_text('dict')) เหมารวมเป็น text "block" เดียวกัน ทั้งที่
ไม่ใช่ย่อหน้าเดียวกันจริง — พอผู้ใช้เลือกทั้ง block มาแก้ ข้อความคนละเรื่องจะถูกรวม/วาดใหม่ปนกันจน
"เพี้ยน" ทางแก้คือไม่เชื่อ block ของ MuPDF ตรงๆ แต่รวมเฉพาะบรรทัดที่ "ดูเหมือน wrap มาจริง" เท่านั้น
(บรรทัดก่อนหน้ากว้างเกือบเต็มความกว้างสุดของ block นั้น) ถ้าบรรทัดก่อนหน้าสั้น (เป็น label/value
แบบสมบูรณ์ในตัวเอง ไม่ใช่ข้อความที่ล้นไปบรรทัดถัดไป) จะถือว่าบรรทัดถัดไปเป็นคนละย่อหน้า/field แยกกัน
ผลคือย่อหน้าที่ wrap จริง (เช่น ข้อความในสเตทเมนต์ธนาคาร) ยังคงถูกจัดกลุ่มรวมเป็นก้อนเดียวเหมือนเดิม
แต่ label/value ในฟอร์มจะถูกแยกเป็นกล่องเลือกทีละบรรทัดแทน ป้องกันการปนกัน

เรื่อง redact ทับด้วยสีขาวเสมอ (แก้บั๊กสำคัญ #4): เดิมโค้ดนี้ fill (1,1,1) สีขาวตอน redact เสมอ
โดยสมมติว่าพื้นหลังหน้าเป็นสีขาว ซึ่งไม่จริงเสมอไป — เอกสารที่ field มีแถบสีพื้นหลัง (เช่น กล่องข้อมูล
ลูกค้าสีชมพู/เทาอ่อนในใบส่งสินค้า) พอ redact ด้วยขาวจะเห็นเป็นปื้นสี่เหลี่ยมสีขาวขัดกับพื้นหลังรอบๆ ชัดเจน
ทางแก้: สุ่มดูสีที่มุมทั้ง 4 ของกล่อง (ก่อน redact) มาใช้เป็นสี fill แทน ถ้าพื้นหลังเป็นสีขาวอยู่แล้วผลลัพธ์
ก็ยังเป็นขาวเหมือนเดิม แต่ถ้าเป็นสีอื่นจะกลืนไปกับพื้นหลังจริงแทน (ดู _sample_background_color)

เรื่องข้อความล้นกล่องลงไปทับแถวถัดไป (แก้บั๊กสำคัญ #5 — เดิมย่อ font อัตโนมัติ, ยกเลิกแล้ว): เดิมโค้ดนี้
เคยแก้ปัญหาข้อความล้นด้วยการย่อขนาด font ลงอัตโนมัติให้พอดีกล่อง แต่หลัง frontend เพิ่มปุ่มลากขยาย/
ย่อกล่องข้อความเองได้แล้ว (ดู EditableTextBox.jsx) ผู้ใช้แจ้งว่าไม่ต้องการให้ระบบไปย่อขนาดที่เลือกไว้เอง
อีกต่อไป — ตอนนี้จึงวาดที่ font size ตามที่ผู้ใช้เลือกตรงๆ เสมอ ถ้าข้อความจะล้นกล่อง ผู้ใช้ต้องลากขยาย
กล่องเองก่อนกดบันทึก (ควบคุมได้ชัดเจนกว่าให้ระบบเดาลดขนาดให้)

เรื่องแก้ไขย่อหน้าเดิมซ้ำไม่ได้ (แก้บั๊กสำคัญ #6): เดิมโค้ดนี้พอแก้ข้อความย่อหน้าไหนไปแล้ว ย่อหน้านั้นจะ
กลายเป็นรูปภาพ (type 1 block ใน page.get_text('dict')) ซึ่ง get_text_blocks() ข้ามไปเสมอ (กรองเอาแต่
type 0 = text block) ผลคือกดบันทึกครั้งแรกแล้ว "หาย" ไปจากรายการที่คลิกเลือกแก้ไขได้ กดแก้ไขซ้ำอีกครั้ง
ไม่ได้เลย ทางแก้: เก็บ "ทะเบียนย่อหน้าที่เคยแก้ไข" ไว้ใน session (session.text_edits ดู
app/core/session.py) แยกต่างหากจากข้อความดิบใน PDF — get_text_blocks() จะเอารายการนี้มาต่อท้ายเป็น
TextBlock ปลอมๆ ที่มี block_id ขึ้นต้นด้วย "edit-" เสมอ ทำให้ยังคลิกเลือกแก้ไขต่อได้เรื่อยๆ
ส่วน replace_text() เวลาได้ block_id ที่ตรงกับทะเบียนเดิม จะถือว่าเป็นการ "แก้ไขซ้ำ" ไม่ใช่แก้ครั้งแรก
และต้องรับ previous_rect (ตำแหน่งที่ย่อหน้านี้วาดอยู่จริงตอนนี้) มาด้วย เพื่อ redact ล้างรูปข้อความเก่า
ที่เคยวาดจาก edit ครั้งก่อนออกให้หมดก่อน (union กับ rect ใหม่) — และเปลี่ยนจาก
images=PDF_REDACT_IMAGE_NONE (เดิมตั้งใจไม่แตะรูปภาพใดๆ ในหน้าเลย กันลบรูปจริงของเอกสารโดยไม่ตั้งใจ)
เป็น PDF_REDACT_IMAGE_PIXELS (ลบเฉพาะพิกเซลของรูปที่อยู่ในกรอบ redact เท่านั้น ไม่ลบทั้งรูปถ้ารูปนั้น
ยื่นออกไปนอกกรอบ) เพื่อให้รูปข้อความเก่าที่เราแทรกเองถูกล้างออกจริงๆ ตอนแก้ไขซ้ำ โดยยังปลอดภัยกับรูปภาพ
จริงอื่นๆ ในเอกสารที่บังเอิญอยู่ใกล้ๆ (จะโดนแค่ส่วนที่ทับกับกรอบ ไม่ใช่ทั้งรูป)

เรื่องแทรกรูปภาพใหม่ + ย้าย/ปรับขนาดรูปเดิมด้วยเมาส์ (แก้บั๊กสำคัญ #7): เดิมโหมดแก้ไขรูปภาพทำได้แค่
"แทนที่" รูปเดิม (replace_image — คงตำแหน่ง/ขนาดเดิมทุกอย่าง เปลี่ยนแค่เนื้อรูป) ผู้ใช้แจ้งว่าต้องการ
(ก) แทรกรูปใหม่เข้าไปในหน้าได้ (ไม่ใช่แค่แทนที่รูปที่มีอยู่แล้ว) กับ (ข) ลากเมาส์ย้าย/ปรับขนาดรูปได้
ทางแก้:
  - insert_image() วางรูปใหม่ลงไปตรงๆ ด้วย page.insert_image() รูปที่แทรกแล้วเป็น image object จริง
    ในเอกสาร ไม่ต้องมีทะเบียนแยกเหมือนข้อความ (get_images() จะเห็นรูปนี้เองในครั้งถัดไปโดยอัตโนมัติ)
  - reposition_image() ใช้แนวทางเดียวกับข้อความ (redact แล้ววาดใหม่): ดึงไบต์รูปเดิมออกมาก่อน (ก่อน
    กรอบเดิมจะถูก redact ทับ) แล้ว redact กรอบเดิม∪กรอบใหม่ด้วยสีพื้นหลังที่สุ่มมา ลบเฉพาะพิกเซลรูปที่
    ทับกรอบนี้ (PDF_REDACT_IMAGE_PIXELS) จากนั้นวาดรูป (ไบต์เดิม) ลงกรอบใหม่ — ได้ผลเหมือน "ย้าย/
    ปรับขนาด" รูปเดิม โดยไม่ไปยุ่งกับรูปอื่นที่บังเอิญอยู่ใกล้ๆ
  - get_image_bytes() คืนไบต์ดิบของรูป (ตาม xref) ให้ frontend เอาไปโชว์เป็นพรีวิวจริงในกล่องลาก
    ย้าย/ปรับขนาด ก่อนกดบันทึกจริง (เดิม get_images() มีแค่ตำแหน่ง/ขนาด ไม่มีเนื้อรูปให้โชว์)

เรื่องกล่องข้อความเดิมเล็กเกินไปหลังเปลี่ยนฟอนต์ให้ใหญ่ขึ้น (แก้บั๊กสำคัญ #8 — ผู้ใช้แจ้งว่าแก้ไข
เลือกฟอนต์/ขนาดใหม่แล้ว หลังบันทึกฟอนต์ดู "เล็กกว่าที่เห็นตอนแก้ไข" และคลิกเลือกย่อหน้าที่แก้ไขไปแล้ว
ไม่ติดอีก): สาเหตุจริงไม่ใช่ font เล็กลง — กล่อง (rect) ที่ผู้ใช้เลือกยังเป็นกล่องเดิมที่พอดีกับข้อความ/
ฟอนต์ขนาดเก่า (เช่น 12pt) พอเปลี่ยนเป็นฟอนต์ใหญ่ขึ้นมาก (เช่น 30pt) โดยไม่ได้ลากขยายกล่องเอง ข้อความจะ
ถูกตัดคำขึ้นบรรทัดใหม่ถี่ขึ้นมาก (เพราะความกว้างกล่องเท่าเดิม) จนจำนวนบรรทัดรวมสูงเกินกล่องเดิมไปมาก —
ฝั่ง frontend เดิม `.edit-inline-text` ตั้ง `height:100%; overflow:hidden` ตายตัวจึง "ครอบ/ตัด" ส่วนเกิน
ไว้เงียบๆ ระหว่างพิมพ์ (ดูเหมือนฟอนต์เล็ก/ข้อความหาย ทั้งที่จริงแค่โดนกล่องบังไว้) และที่ร้ายกว่าคือ
กล่องเดิม (เล็ก) นี้เองถูกเก็บเป็น "กรอบคลิกเลือก" ในทะเบียน session.text_edits โดยไม่ขยายตาม — พอบันทึก
จริงแล้วเนื้อหาจริงล้นลงไปไกลเกินกรอบเดิม (มองเห็นบนหน้าเอกสาร) แต่กรอบที่คลิกได้ยังเล็กเท่าเดิม คลิก
บนข้อความที่เห็นจริงจึงไม่ติด (คลิกไม่โดนกรอบ .edit-box-text ที่ยังเล็กอยู่) ทางแก้ 2 จุด:
  1. Backend (ฟังก์ชันนี้): คำนวณ "ขอบล่างสุดจริง" ของทุกบรรทัดที่เรนเดอร์แล้ว (content_bottom_pt)
